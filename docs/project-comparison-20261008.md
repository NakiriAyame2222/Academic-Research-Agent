本次检查包括项目源码、现有测试和指标文件、2026-09-29 验收记录，以及同类项目的官方 README、发布记录和论文。只新增这份分析文档，未修改应用实现；做了三个不调用外部服务的内存级最小复现，未重新运行完整测试、真实模型调研或 Docker 构建。旧验收记录中的 172 项通过是当时的离线/模拟验收结果。

**当前已经具备的能力**

项目有单篇论文问答与主题调研两条业务路径，支持 arXiv 搜索、全文下载、稠密向量与稀疏 TF-IDF 混合检索、Chroma 与简易后端降级、研究反思与补证、会话记忆、报告生成和引用编号审计。

**第一项重点：从引用编号检查升级到逐条结论的证据核验**

当前 `agent/citation_check.py:45` 用正则抽取 `[Sx]` 并检查编号是否存在。`valid_reference_rate` 是编号有效率；`citation_coverage` 是已使用证据 ID 数占可用 ID 数的比例。这两个值都不能直接解释为“结论正确率”或“事实有证据支持的比例”。

本次用“模型准确率 99% [S1]”作为正文、用“该研究未报告准确率”作为 S1 摘录输入，当前审计仍返回 `valid_reference_rate=1.0` 和 `citation_coverage=1.0`。这符合当前编号检查的实现，也说明其能力边界。

参考 PaperQA2 的证据处理、OpenScholar 的归因与反馈流程，建议增加结构化记录：

```text
claim_id → claim_text → evidence_ids → source_span
         → verdict: supported / contradicted / insufficient
         → reviewer_reason
```

先覆盖报告里的数字、方法效果比较和主要结论。证据核验可以由独立步骤完成，并保留人工抽查入口；自动核验器也应有自己的标注验证集，不能把模型判断直接当作真值。对资料不足的结论进行限定、补证或移除，并向用户展示原文。

验收关注“可核验事实中有充分支持的比例”“引用是否真的支持对应断言”“错误数字/张冠李戴能否被发现”。保留现有编号审计，给指标使用准确名称。

**第二项重点：建立能支撑简历结论的评测体系**

目前已有评测基础，但有三处限制：

- `tests/artifacts/retrieval_metrics.json` 来自 6 份合成文档、30 条查询；`tests/conftest.py:35`、`:317` 使用按关键词映射的 `KeywordEmbedder`。该数据适合回归验证，Recall@1=1.0 不能代表真实论文检索水平。现有结果里 hybrid 和 sparse 的 MRR 都为 1.0，尚不能证明引入向量后带来了提升。
- `tests/test_real_papers.py` 已经有 15 条真实语料查询及端到端入口，应继续完善。当前检索相关性主要按目标文件名判断，尚不能验证找到的段落是否足以支撑答案；端到端用例在模型降级时也允许检查检索/引用基础链路。这些结果需要与真实模型成功生成的结果分开统计。
- `tests/test_claude_code_baseline.py:76` 的论文问答答案是固定文本，`:85`、`:87` 的正确性与证据支持标记直接为 `True`。它可以保留为示例夹具，但不应作为真实 Claude Code 运行成绩。先更名说明，或接入真实执行记录再对比。

建议先建立 30 道人工标注的困难问题，再扩到 100 道，覆盖单篇定位、跨论文比较、中文问英文论文、文献结论冲突和资料中无答案。每题记录可接受结论、证据原文及应避免的错误。

| 对比层 | 公平条件 | 建议指标 |
| --- | --- | --- |
| 检索模块 | 固定论文与标注，分别运行 sparse、dense、hybrid、hybrid+reranker | 片段级 Recall@k、nDCG、检索耗时、无答案误召回 |
| 回答与综合模块 | 固定模型、论文和证据预算，对比直接长上下文、普通 RAG、当前流程、改进流程 | 结论正确性、证据支持率、引用准确性、跨文献覆盖、资料不足时的回答表现 |
| 完整在线调研 | 固定题目、时间范围、预算，并记录各自搜索工具和来源限制 | 报告质量、成功/降级/失败率、延迟、模型用量和成本 |

检索 top-k 与指标 k 也应一致：`tests/test_retrieval_quality.py:19` 当前只取 5 条却报告 nDCG@10。建议改为取足 10 条，或明确报告 nDCG@5。

保留模型版本、提示词版本、数据快照、原始运行记录；对随机性较大的端到端任务进行重复采样并报告波动。先得到基线，再确定提升目标。外部项目论文中的分数不应直接搬来和本项目不同条件的分数比较。

**第三项重点：提升论文检索和 PDF 理解质量**

当前稀疏部分是 TF-IDF，融合为固定 dense 0.7 / sparse 0.3，尚未看到独立的学习型重排模块。可以先把召回扩大到 20—40 个候选片段，再用 reranker 选 5—8 个高质量片段；这些数值仅作为实验起点，由评测确定。对比当前加权融合与 RRF，避免仅凭直觉更换算法。

`rag/loader.py` 主要使用 pypdf/PyMuPDF 抽取文本与字符切分。下一步可引入解析器接口，对复杂论文尝试 Docling 等结构化解析方案；先选双栏、表格和公式密集的样本验证收益，再决定默认方案。保留页码、章节及精确原文位置，并记录解析质量和失败原因。

另外，结构化切块路径的 `char_start` 当前按块长度累加，没有反映重叠和分隔符处理。这是源码检查发现，当前环境未运行该可选分支；做 PDF 原文高亮之前需要专门验证偏移定位。

检索源可从 arXiv 扩充到 Semantic Scholar/OpenAlex，并按 DOI/arXiv ID 去重；增加时间范围和版本信息。最新进展应同时考虑经典基线与近期工作，不能只按引用量筛选，否则容易排除新论文。保留“只有摘要”和“已获得全文”的明确区别。

**第四项重点：把研究过程做成用户能检查的工作流**

已有运行中追加/取消控制，建议继续深化：复杂主题先展示可编辑研究范围、时间限制和论文筛选条件；让用户查看选中的论文和排除理由。简单问题可以直接开始，不必每次额外确认。

`web/src/components/CitationPanel.tsx` 已能联动高亮引用、显示摘录和 arXiv 链接。下一步让点击结论能打开对应 PDF 页并定位原文，形成“结论—证据—原文”闭环。先完成前述页码与偏移修正。

报告可新增有证据来源的文献比较矩阵：方法、数据集、评价指标、实验设置、局限、论文版本。同一指标只有在实验条件可比时才并列比较，条件不同应明确说明。之后再增加 BibTeX/Zotero 导出、局部重写与报告版本差异。

一个适合展示的完整案例是：开始调研 Agent Memory → 运行中增加长期记忆评测方向 → 移除无关方向 → 查看跨论文比较 → 点击关键结论检查原文 → 查看本次消耗与未解决问题。

**第五项重点：记录成本，并统一两条运行路径的核心语义**

当前有进度和工具调用展示，但模型适配器 `config.py:133` 未把完整响应的 usage 统一送入运行记录；阶段级模型配置、成本统计及总预算控制还有空间。

参考 Open Deep Research，给规划、摘要、深读、反思和最终写作分别配置模型；先计量每阶段调用次数、输入/输出 token、耗时和重试，再决定怎样分配模型。记录 `run_id/topic_id/stage`，让用户能追踪慢在哪一步、钱花在哪一步。已有进度回调可作为接入点。

应把达到轮数上限、token 上限、时间上限、用户取消、证据充分分别记录为不同终止原因。缓存键应包含模型、提示词和内容版本，避免报告成本下降时实际复用了不匹配结果。

项目同时存在 `agent/graph.py` 的图执行和 `agent/topic_scheduler.py` 的 Web 子主题管线，后者也包含深读、反思及汇总逻辑。优先抽取共用的证据、引用、停止原因和写作服务，让 CLI/Web 共用语义；保留调度器的追加、取消、代次和幂等约束。当前 `graph.compile()` 没有接 LangGraph checkpointer，但项目已有自建持久化，不能据此认定“没有断点恢复”。是否换存储机制，应由现有故障模型和多进程需求决定。

**项目展示和部署的收尾工作**

- 增加项目根 README：一句话定位、功能演示、架构图、最短启动步骤、配置模板、真实报告样例、评测方法和已知限制。当前说明主要分散在 `web/README.md`、MCP 文档和异步主题调研文档中。
- 将长期有用的验收用例及浏览器场景纳入项目测试目录与 CI，避免核心证据只留在 `tmp/`。测试取消、恢复、引用来源对应与真实启动路径，比增加只镜像实现的测试更有价值。
- 后端依赖当前多为最低版本约束，可补可复现的锁定方案；前端镜像构建使用已有 lockfile 配合 `npm ci`。
- Dockerfile 第 17 行把多个源目录复制到同一工作目录：按普通 Docker COPY 目录语义会复制目录内容，可能丢失预期包目录结构；它也未包含本地 `skills/`。建议改为明确保留各包路径，纳入镜像启动及技能加载检查。此项为静态审阅，尚未实际构建镜像。
- 如果确实要面向多人部署，再提高鉴权、会话/文件归属校验、任务队列和共享存储的优先级。`api/main.py` 当前明确以单进程单用户设计；单人作品展示阶段可以先把这一范围写清楚。

**建议实施顺序**

| 顺序 | 一次可交付的结果 | 完成标准 |
| --- | --- | --- |
| 1 | 页码、未命中回退、轮数耗尽语义修正；评测命名纠正 | 三个具体场景有准确行为；模拟与真实成绩明确分开 |
| 2 | 30 题人工标注评测集和当前基线 | 能重复生成质量、失败、耗时与成本记录 |
| 3 | reranker 与结论证据核验实验 | 在固定条件下展示收益及增加的成本，保留失败案例 |
| 4 | 原文定位、文献矩阵和动态调研演示 | 用户能从结论核对来源，并完整演示已有追加/取消/恢复能力 |
| 5 | 共用业务服务、README、CI 和镜像启动验证 | 他人可按文档复现，CLI/Web 的关键语义一致 |

若只选择三个投入方向：先把证据链修准确，再做真实评测，随后加入可量化收益的重排与核验。简历可以描述设计和实测结果，性能提升百分比等数字应在公平实验完成后填写。

针对已确认的双重目标，每一阶段都应同时交付实际功能和可解释的技术证据：

| 阶段 | 长期自用的收益 | 面试可展开的技术问题 | 应保留的成果 |
| --- | --- | --- | --- |
| 1. 证据准确性 | 引用页码准确；资料不足时如实说明；错误结论能追查 | 元数据不变量、检索拒答边界、运行终止原因与质量判断的区别 | 缺陷复现、修复前后行为、结论与证据对应样例 |
| 2. 真实评测与检索改进 | 中文问英文论文、相近方法比较时更容易找到正确段落 | 稀疏/稠密召回取舍、融合与重排、困难负例、消融实验、质量与延迟的权衡 | 固定评测集、基线结果、改进结果、失败分析及成本记录 |
| 3. 研究工作流与成本 | 原文核对、研究中调整方向、中断后继续、预算可控 | 调度状态机、取消传播、迟到提交拒收、幂等与恢复、阶段级用量计量 | 状态转换图、故障场景验证、完整演示和运行记录 |
| 4. 日常使用与复现 | 重复使用论文库时减少等待；环境可稳定重建 | 内容版本与缓存失效、增量索引、入口共享业务语义、依赖锁定 | 可启动环境、增量索引前后耗时、操作说明与真实报告样例 |

长期自用优先按本地单用户设计，补齐论文库复用、按内容和解析/模型版本判断缓存有效性、增量索引、单次研究预算与报告导出。多租户、分布式任务队列和通用代码执行平台暂列后续。已有异步主题调度应保留为重点：先补足故障验证与设计说明，评估重复业务逻辑后再做局部重构。

面试展示应围绕“遇到什么实际问题、为什么选这个设计、怎样证明有效、付出了多少成本”组织。建议形成一份可现场操作的演示、一组可复现的对比实验和一份调度/证据设计说明；简历中的技术点和数字都能回溯到这三类材料。
